# Remediation review and proposed optimization plan

> Follow-up implementation: see [implementation status, verification and operating instructions](reliability-implementation-2026-09-05.md). The assessment below describes the earlier review snapshot.

Review date: 2026-09-05. Scope: the current working tree, including substantial remediation that was already committed or in progress when this review began. Existing changes were preserved. This is not a deployment certification: no production database, object store, credentials, or remote Git history was changed.

## Executive assessment

The earlier creation, shared-playback, attachment, authorization, startup, dependency, and aggregation findings had largely been addressed in source. Several follow-on changes were incomplete or introduced regressions. This pass completed those code paths and added executable regression coverage. The remaining release gates are real MinIO/Compose recovery verification and deployment-specific secret/backup checks; the larger reliability, performance, and UX proposals below are **for review, not implemented in this pass**.

## Verification performed

- `server: npm test`: 21 passing tests covering access, grants, configuration, creation, shared comments, disk uploads, range parsing, transfer failures, ZIP success/failure, metadata, cover processing, and auth outages.
- `server: npm run test:integration`: real temporary PostgreSQL and real HTTP routes; only object transport is simulated. Covers concurrent/idempotent migrations, custom-bucket backfill, stable version numbering, concurrent uploads/deletes/quota reservations, sharing, microsecond pagination, attachments, cover processing, admin totals, revocation, cascade deletion and outbox retry. Local embedded PostgreSQL is 18; CI is configured for production-major PostgreSQL 15.
- `python3 scripts/test_restore_validation.py`: six passing tests, including corruption, omitted checksums, archive traversal/links, overlapping targets, existing data preservation, and persisted override output.
- Bash syntax checks for backup, restore, and restore-drill helpers.
- Client production build passes. Output: approximately 444.4 kB JavaScript / 118.7 kB gzip; this is a build measurement, not a browser-performance benchmark.
- Dependency audits: client zero vulnerabilities; server high-severity gate passes with seven moderate advisories (`qs`/Express and MinIO parser dependencies). Audit results are a point-in-time snapshot.

Not verified: browser/device UX, actual MinIO transport or full backup/restore round-trip, production-size query plans/RSS/latency, remote CI execution, deployment credentials, and off-host recovery. The new tests substantially improve confidence but do not replace those checks.

## Release checklist for this remediation

1. Review the entire dirty diff together with pre-existing work; include all new helper files, tests, and migrations in the same change set. Do not ship routes without their migrations or lockfiles.
2. On an isolated Docker-capable host, build the current API image, seed known audio/covers/attachments, create a format-3 backup, run `restore-drill.sh`, and verify playback/downloads using real MinIO. Repeat with custom DB names, bucket names, and bind paths. Deliberately corrupt a backup and remove an object; neither case may report success.
3. Run CI on PostgreSQL 15 and execute the existing `server/db/performance-explain.sql` against a representative restored dataset. Capture actual plans rather than assuming each small test uses an index.
4. Confirm previously exposed secrets were rotated in every deployed system and distributed artifacts/clones were handled. Confirm encrypted, access-restricted off-host backups exist and the keys are recoverable.
5. Take a verified pre-migration backup and schedule a maintenance window. Migration 004 changes constraints, can repair invalid legacy ordering/pointers, and locks tables; it is not a zero-downtime migration. If it was already applied, do not edit its ledger or rerun it blindly; migration 005 supplies the new lifecycle guards.
6. Deploy code and schema together, smoke-test login/create/upload/share/download/delete, and observe pending-deletion backlog. Roll back schema/data only through a verified restored snapshot; never mix an old DB with a newer object-store snapshot. Use the printed persistent Compose override after restore.

## Proposed next work — approval requested before integration

The sequence prioritizes reliability of core workflows, then measurable performance, then UX refinement. Estimates are rough engineering effort, excluding infrastructure delays. Targets below are proposed acceptance criteria, not measured current guarantees.

| Priority / work package | Scope and rationale | Acceptance criteria | Dependency / effort |
| --- | --- | --- | --- |
| **R1 — Real-service and browser release gates** | Add isolated PostgreSQL 15 + MinIO CI, a seeded full recovery drill, and browser tests for owner/visitor playback, seeking, sharing, uploads, session expiry and mobile navigation. Add fault injection for storage/DB disconnects and process restart during upload/deletion. | Recovery reproduces DB counts and every referenced media hash; corrupted/missing data fails closed; no cross-owner access; core browser journeys pass. Publish test artifacts without tokens or secrets. | First; API + infrastructure owner; 3–5 days. |
| **R2 — Request/process lifecycle** | Graceful SIGTERM drain, explicit DB statement/acquisition budgets, abortable storage operations, bounded global upload/export concurrency, separate liveness/readiness, and rate-limit policies that do not turn repeated health/media requests into false outages. | Controlled shutdown during upload/export leaves either a committed resource or reclaimable stage; stalled dependencies have bounded failure time; health checks do not consume ordinary user limits; no dangling streams or checked-out DB clients. | After R1; backend owner; 3–4 days. |
| **R3 — Grant renewal and revocation semantics** | Refresh media grants near expiry/on recoverable playback failure while preserving owner versus playlist-share authorization. Decide whether disabling sharing revokes existing media URLs immediately or after a documented bounded TTL; add a resource/share generation if immediate revocation is required. | A queue opened longer than the grant TTL still plays/seeks after authorized renewal; revoked access cannot renew; expiry errors are actionable; no session JWT appears in a URL. | Product decision on revocation semantics, then backend/frontend; 2–4 days. |
| **P1 — End-to-end bounded library loading** | Replace `requestAllPages` accumulation with incremental/query-cached pages. Add server-side search/filter/sort and paginated playlist detail; keep reorder semantics explicit across pages. Virtualize long collections only after measurement. | At 10,000 tracks / 100,000 comments, first useful page fetches only one bounded page; no full-library prerequisite to render; no duplicates/skips while paging; scrolling/search remain responsive. Proposed first-page p95 <300ms on agreed reference hardware. | R1 baseline and API contract review; full-stack owner; 4–6 days. |
| **P2 — Workload/query budgets** | Measure `EXPLAIN (ANALYZE, BUFFERS)`, query counts, p95/p99 latency and RSS on representative data. Restrict admin aggregation to requested users where beneficial. Set export concurrency limits; consider persistent export jobs/progress/cancellation only if measured size/duration warrants them. Add snapshot/retention semantics for exports concurrent with deletion. | Fixed-volume export memory stays bounded as library size increases; no database query per reordered item; memory/latency regressions fail a repeatable benchmark; incomplete exports never become successful downloadable artifacts. | P1 baseline, R2 limits; backend owner; 3–5 days. |
| **U1 — Player/upload/error recovery** | Clear buffering/expired-link/offline states, retry and cancellation, distinguish uploaded from fully processed/saved, preserve edited drafts on recoverable failures, and accessible destructive-action confirmations. Avoid optimistic success before persistence. | Browser tests cover offline→online, interrupted uploads, storage error, and expired grant; drafts survive failed saves; cancellation does not create an active DB row; all actions are keyboard accessible and announced appropriately. | R1/R3; frontend + UX owner; 3–5 days. |
| **U2 — Bundle and accessibility refinement** | Lazy-load admin/settings/heavy secondary routes; assess image decode/layout shifts and list virtualization. Audit focus order, keyboard cover upload, screen-reader labels/live regions, mobile player controls and contrast. | Proposed ≥20% reduction in initial-route JS gzip versus the current ~118.7kB baseline, without delayed playback readiness; no serious automated accessibility findings plus manual keyboard/screen-reader completion of core journeys. | P1 and UX review; frontend owner; 2–4 days. |
| **R4 — Operations and residual security** | Structured request IDs and redacted errors; metrics/alerts for pending/failed deletion, stale stages, quota drift, missing objects, backup age and restore success. Design a dry-run inventory tool for historical unregistered objects with quarantine before deletion. Upgrade or safely override remaining vulnerable transitive parsers only with compatibility tests; review trust-proxy topology and storage least-privilege credentials. | Dependency audits clean at the agreed threshold; representative alerts fire in failure drills; logs contain no bearer grants/passwords; orphan inventory makes no mutations by default; deletions require a reviewed manifest and recovery window. | R1/R2, deployment owner; 3–5 days. |

### Suggested integration sequence

- **Wave 1:** approve/merge the remediation after the release checklist; implement R1 and R2. Do not combine this with a broad framework rewrite.
- **Wave 2:** agree grant semantics and performance baselines; implement R3, P1, then measured P2 changes in independently reversible PRs.
- **Wave 3:** review UX flows and acceptance targets; implement U1/U2, then operational tooling and residual security work in R4 (urgent security fixes can move earlier).

Review choices: immediate versus TTL-bounded share revocation; target maximum supported library/upload size and reference hardware; desired recovery-point/recovery-time objectives; and whether exports should become durable background jobs. These decisions govern the next implementation, not the completed bug fixes.
